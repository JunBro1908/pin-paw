# 데이터셋 구성 이유 (Rationale)

각 실험 데이터셋이 **왜 그런 형태로 구성되었는지** 정리한 문서입니다.

---

## Insight 1: 흰색 기준 3단계 유사도 (cut-off / 단계별 점수)

**기준**: **흰색** 한 가지. 여타 색을 전부 흰색과 비교한다.

### 1-1. `insight1_color_cutoff.csv` (프롬프트 문장 전체)

**구성**

- **31행**: id=0 = **기준(흰색)** 문장, id=1~30 = **비교할 케이스 30개** (단계별 10개씩). 컬럼: `id`, `tier`, `text_sentence`, `note`. **tier**: 0=기준(흰색), 1=흰색과 같은 것, 2=애매, 3=흰색과 다른 것.
- **tier 1 (10개)**: 하얀색, 하얗습니다, 아이보리, 크림색, 연한 흰색, 밝은 흰색, 흰 털, 새하얗습니다, 뽀얗습니다, 흰색빛. **tier 2 (10개)**: 회색, 연한 회색, 밝은색, 어두운색, 골드, 금색, 베이지, 카키, 은색, 연한 갈색. **tier 3 (10개)**: 검정, 검은색, 까맣습니다, 갈색, 밤색, 짙은 갈색, 빨간색, 주황색, 노란색, 파란색.

**왜 이렇게 했는지**

- **프로덕션과 동일한 입력**을 쓰기 위함. 우리가 임베딩하는 건 “문장 전체”이므로, 문장이 길수록 색상 정보 외에 “유실 반려동물”, “털 색상” 같은 공통 문맥이 임베딩에 섞여 들어감.
- 이 공통 문맥 때문에 **같은 색 vs 다른 색** 유사도 차이가 작게 나올 수 있음. 그래서 “문장 전체” 실험으로 **현재 파이프라인의 한계**를 먼저 확인하는 것이 목적.
- `color_named`(white/black/brown 등)은 **규칙 기반(네임드 스페이스)** 비교용 라벨. `expected_tier`(similar_same / ambiguous / not_similar)는 “같은 색끼리 유사, 다른 색끼리 비유사”가 얼마나 잘 나오는지 **검증용 기대 구간**.
- **동의어·인접색·패턴·모호 표현**을 넣은 이유: 실제 유저 입력이 “흰색”, “하얀색”, “아이보리”, “얼룩덜룩” 등 다양하기 때문에, 이들이 임베딩 공간에서 어떻게 묶이는지 보려고.

### 1-2. `insight1_color_only.csv` (색만)

**구성**

- 한 행 = **색상 값만** 한 단어/구 (프롬프트 문구 없음).
- 컬럼: `id`, `text_color_only`, `color_named`, `expected_tier`, `note`.
- `text_color_only`: "흰색", "하얀색", "아이보리", "연한 흰색", "흰색에 검은 점이 있습니다" 등 **색만 들어가는 부분**만.

**왜 이렇게 했는지**

- **프롬프트 문맥을 제거**했을 때 임베딩이 어떻게 달라지는지 보기 위함.
- 문장 전체를 쓰면 “이 유실 반려동물의 털 색상은 …”이 모든 행에 공통으로 들어가 **색 차이보다 문맥이 지배적**일 수 있음. **색만** 넣으면 색상 표현 간 유사도가 더 잘 드러날 수 있음.
- 같은 `id`·`color_named`·`expected_tier`를 유지해서 **프롬프트 문장(insight1) vs 색만(insight1_color_only)** 결과를 **동일한 기준으로 비교**할 수 있게 함.
- 실험 질문: “색만 넣었을 때 same_color / other_color 구분이 더 뚜렷한가?” → 뚜렷하면 **색상은 규칙/토큰으로만 비교하고, 임베딩은 색만 쓰는 방식** 등을 검토할 수 있음.

## Insight 2: 특이사항 비정형 vs 정형(태그)

### `insight2_special_traits.csv`

**구성**

- 한 행 = **메모 필드에 넣을 문장 1개** (비정형 자유문 또는 정형 태그 문장).
- 컬럼: `id`, `meaning_group`, `content_type`, `text_to_embed`, `tag_ids`, `note`.
- **의미 그룹(meaning_group)** 별로 **free_text** 1개 + **tag_sentence** 1개 쌍. 같은 의미를 “자유 메모”와 “태그를 문장으로 풀어 쓴 것” 두 형태로 둠.

**왜 이렇게 했는지**

- **비정형(자유 메모)** vs **정형(태그)** 중 어떤 입력이 매칭에 더 낫는지, 또는 “태그는 참고용만 쓸지”를 실험하려고.
- **동일 의미**를 두 형태로 넣어서, 임베딩 유사도가 **의미를 잘 반영하는지**를 봄. free_text–tag_sentence 유사도가 높으면 “태그로 받아도 의미가 잘 전달된다”는 근거가 됨.
- **장착/외형/행동** 등 **실제 트레이트 태그**와 대응하는 문장을 쓴 이유: 실서비스에서 쓰는 태그(id)와 동일한 체계로, 나중에 “태그 기반 추천”과 “메모 임베딩”을 같이 쓸 때 비교하기 위함.
- **희귀·일반 태그**가 섞여 있음: 태그 종류에 따라 free vs tag 유사도 차이가 나는지도 보려고.

## Insight 3: 유사도 구간·정규화(실제 min/max)

### `insight3_normalization.csv`

**구성**

- 한 행 = **비교할 문장 쌍 1개** (text_a, text_b).
- 컬럼: `pair_id`, `text_a`, `text_b`, `expected_rank`, `description`.
- `expected_rank`: 1=가장 유사(완전 동일) ~ 5=가장 비유사. **의도한 유사도 순서**를 표시.

**왜 이렇게 했는지**

- **코사인 유사도가 이론상 0~1**이어도, 실제 데이터에서는 **특정 구간(예: 0.64~1.0)** 에만 몰릴 수 있다는 가정을 검증하려고.
- **의도한 순서(expected_rank)** 를 두어, 실측 유사도가 이 순서와 맞는지, 그리고 **실제 min/max**를 구해 **0~100 정규화**를 적용했을 때 스케일이 어떻게 나오는지 보려고.
- **완전 동일 / 동의어 / 종만 다름 / 종·색·크기 모두 다름 / 완전 다른 동물**처럼 **유사도 스펙트럼**을 골고루 넣은 이유: min/max와 분위수를 추정할 때 구간이 한쪽으로 치우치지 않게 하려고.
- **색만 비교**(흰 vs 검), **메모만 비교**(동일 의미 vs 다른 의미), **메모 유무만 차이** 같은 행을 넣은 이유: **텍스트 종류(색/메모/종 등)** 에 따라 유사도 분포가 어떻게 다른지도 해석하려고.

## 요약

| 데이터셋                    | 구성 핵심                                | 목적                                                          |
| --------------------------- | ---------------------------------------- | ------------------------------------------------------------- |
| **insight1_color_cutoff**   | 프롬프트 문장 전체(색 포함)              | 현재 파이프라인과 동일 조건에서 색상 cut-off·단계별 점수 검토 |
| **insight1_color_only**     | 색상 값만(프롬프트 제외)                 | “색만” 넣었을 때 유사도가 더 잘 구분되는지 비교               |
| **insight2_special_traits** | meaning_group별 free_text + tag_sentence | 비정형 vs 정형(태그) 입력의 매칭 적합성·참고용 활용 검토      |
| **insight3_normalization**  | expected_rank가 있는 문장 쌍들           | 실제 유사도 구간·min/max·0~100 정규화 효과 검토               |
