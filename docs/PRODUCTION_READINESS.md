# 실서비스·다중 클라이언트 검토 (Production Readiness)

여러 클라이언트가 동일 백엔드/앱을 사용할 때, 실서비스 전에 점검·대응이 필요한 항목을 정리한 문서입니다.

---

## 1. 인증·세션

| 항목     | 현재 상태                       | 실서비스 시 고려사항                                                                                                                                                                                                                               |
| -------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 인증     | Supabase Auth (JWT)             | 클라이언트별로 **Supabase 프로젝트를 분리**할 경우, 각각 `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`를 다르게 배포해야 함. 동일 프로젝트에 여러 앱(도메인)이 붙는 경우, Supabase 대시보드에서 해당 도메인 Redirect URL 등록 필요. |
| Anon Key | 프론트에 노출 (`NEXT_PUBLIC_*`) | 읽기/쓰기는 RLS로 제한되나, 키 자체가 노출되므로 **클라이언트별 키 분리**는 불가. 프로젝트 단위로 1 anon key.                                                                                                                                      |

---

## 2. 데이터 격리 (RLS·테넌트)

| 항목      | 현재 상태                    | 실서비스 시 고려사항                                                                                                                                                                                   |
| --------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 격리 단위 | **유저 단위** (`auth.uid()`) | 조직/팀/테넌트(예: `organization_id`) 개념 없음. "여러 클라이언트"가 **서로 다른 사업체·도메인**이라면, 현재 구조는 **동일 DB를 공유하는 다중 브랜드**에 가깝고, 유저·유실글·제보가 모두 한 풀에 섞임. |
| 권장      | -                            | 클라이언트(테넌트) 단위로 데이터를 완전 분리하려면 `organization_id`(또는 `tenant_id`) 컬럼 추가 및 모든 RLS 정책에 테넌트 조건 추가, 가입/초대 시 테넌트 배정 플로우 필요.                            |

---

## 3. API

| 항목        | 현재 상태                                           | 실서비스 시 고려사항                                                                                                                       |
| ----------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Rate limit  | atomic DB fixed-window + IP/user 이중 제한          | 검색 30/분·300/일/IP, 지도 120/분/IP 등 route별 preset이 구현됨. 공개 전 실제 DB 50-way 경쟁과 Vercel forwarding-header 검증이 필요.       |
| 추천 API    | `GET /api/v1/recommendations` 캐시 TTL **180초**    | 동일 `lostPostId`·조건에 대해 3분간 캐시. 트래픽은 줄지만, 새 제보 반영이 최대 3분 지연될 수 있음. 필요 시 TTL 조정 또는 무효화 전략 검토. |
| 에러 메시지 | 한글 메시지 반환 (예: "유실글을 찾을 수 없습니다.") | 그대로 노출되므로, 클라이언트별 메시지 커스터마이즈가 필요하면 코드/상수 분리 또는 다국어 구조 검토.                                       |
| 목록 조회   | `limit=50` 등 고정값 다수                           | `lost-posts`, `sightings` 등 목록 API에 하드코딩된 limit. 대량 데이터 시 페이지네이션·cursor 도입 권장.                                    |

## 4. 환경 변수·클라이언트별 설정

| 변수                                      | 용도                             | 다중 클라이언트 시                                                                                                                                                                                                                    |
| ----------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_SUPABASE_URL`                | Supabase 프로젝트 URL            | 클라이언트별 프로젝트 사용 시 빌드/배포마다 다른 값 필요.                                                                                                                                                                             |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY`           | Supabase anon key                | 위와 동일.                                                                                                                                                                                                                            |
| `NEXT_PUBLIC_NAVER_CLIENT_ID`             | 네이버 지도 API (클라이언트)     | 지도·위치 선택 모달에 사용. 브라우저에 노출되므로 NEXT*PUBLIC* 접두사 필요.                                                                                                                                                           |
| `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET` | 네이버 검색 API(지역 검색, 서버) | 위치 선택 모달의 **장소명 검색**에 사용. **네이버 개발자센터(developers.naver.com)** 에서 검색 API 설정 후 발급. 지도와 동일 앱이면 NAVER_CLIENT_ID는 NEXT_PUBLIC_NAVER_CLIENT_ID와 같은 값으로 설정. 미설정 시 장소 검색만 비활성화. |

## 5. 지도·추천 UX (7-5 연동)

| 항목                  | 내용                                                                                                                                                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 지도 북마크 별 미표시 | **반영 완료.** 추천 → "지도에서 보기" 진입 시 `initialLostPostId`가 있으면 해당 유실글 1건만 `GET /api/v1/lost-posts/[id]`로 로드해 `myLostPosts`에 넣어, 상세 패널에 북마크 별이 노출되도록 함. (SDD 7-5.6.1 해결.) |

## 6. 스토리지 (Supabase Storage)

| 항목 | 현재 상태                                        | 실서비스 시 고려사항                                                                                                                   |
| ---- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 버킷 | `lost`(유실글 사진), `sightings`(목격 제보 사진) | 테넌트 구분 없음. 클라이언트별로 버킷을 나누거나 경로 prefix(예: `{tenant_id}/`) 도입 시, 업로드/조회 경로 및 RLS 정책 전반 수정 필요. |

---

## 7. 백그라운드·크론

| 항목 | 현재 상태                                                             | 실서비스 시 고려사항                                                                                                                                     |
| ---- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 크론 | embedding 5분, upload cleanup 일 1회 | 두 endpoint 모두 `CRON_SECRET` 누락 503·오류 401로 fail-closed한다. embedding은 SKIP LOCKED lease와 최대 3회 backoff를 사용하며 staging Cron·동시 호출 검증은 남아 있다. |

## 8. 보안·운영

| 항목          | 권장 사항                                                                                                              |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `.env.local`  | 저장소에 커밋하지 않기. 실서비스 키는 배포 환경 변수로만 관리.                                                         |
| Supabase RLS  | 모든 유저 데이터 테이블에 RLS 적용 여부 재점검. (7-5: `user_sighting_views`, `lost_post_sighting_claims` 등 문서화됨.) |
| API 에러 로깅 | `console.error` 외에 실서비스용 로깅·알림 연동 시 유리.                                                                |

## 9. 체크리스트 요약

- [ ] **다중 클라이언트**
  - 동일 프로젝트 다중 도메인 vs 프로젝트/DB 완전 분리 결정.
  - 테넌트 분리가 필요하면 `organization_id`(또는 유사) 및 RLS·가입 플로우 설계.
- [ ] **API**
  - Atomic rate limit 구현 완료; 실제 DB 50-way·staging spoof 검증.
  - 추천 캐시 TTL·무효화 전략 검토.
- [ ] **환경 변수**
  - 클라이언트별 Supabase/지도 설정 분리 방식 결정 및 배포 파이프라인 반영.
- [x] **UX**
  - 추천 → 지도 진입 시 북마크 별 노출 반영 완료 (initialLostPostId 시 해당 유실글 1건 로드).
- [ ] **스토리지·크론**
  - 테넌트/용량 확장 시 스토리지 경로·크론 부하 검토.

이 문서는 실서비스 및 다중 클라이언트 대응 시 공통으로 점검할 항목을 제공하며, 필요에 따라 프로젝트별로 보완해 사용하면 됩니다.
